The red block, implemented as regalu.sv, is the execution and write-back datapath slice of the Reduced RISC-V CPU. It ties together three components: the register file, the operand multiplexer, and the ALU. The register file contains 32 registers x0–x31, with x0 hardwired to zero so reads from register 0 always return 0 and writes to register 0 are ignored. It has two asynchronous read ports (for rs1 and rs2) and one synchronous write port (for rd), which updates on the rising clock edge when regwrite is asserted. The value of register x10 is exposed directly as a0 for debugging and testing.

The mux decides whether the ALU’s second input is a register value (RD2) or an immediate. alusrc=0 selects RD2, whereas alusrc=1 selects imm. This allows both register-register and register-immediate operations. The ALU performs 32-bit add or subtract depending on aluctrl, where aluctrl=0 performs addition and aluctrl=1 performs subtraction. The ALU outputs aluout, and also drives eq, which becomes 1 when aluout equals zero. In the full CPU this eq signal is used for BEQ decisions.

The behaviour of the entire red block can be summarized as: read rs1 and operand2 (either rs2 or imm), compute aluout, optionally write the result back into register rd if regwrite is asserted, and continuously expose x10 as a0. This makes the red block the core of arithmetic, comparison, and writeback logic.

To verify correctness, we use a C++ testbench built with Verilator and GoogleTest. The C++ model Vregalu is driven by a tick() function that simulates one full clock cycle. Before each test, we reset all control and data inputs to known values. The tests cover immediate addition (writing x10 = imm and checking aluout and a0 match), register-register addition (loading values into registers, adding them, and verifying the ALU result), and subtraction with equality detection (loading identical values into two registers, subtracting them, and confirming aluout=0 and eq=1). These tests confirm correct register reads, writeback, mux selection, ALU arithmetic, and EQ flag behaviour.

In addition to the automated GTest verification, we built an visual Vbuddy demonstration. Three Vbuddy seven-segment displays show aluout, a0, and eq. The LED bar lights fully when eq=1. To make the behaviour human-readable, the simulation is slowed down so each output value remains visible. The demonstration cycles through three phases. First is a count-up phase where we repeatedly perform an ADDI-style operation: rs1=x0, rd=x10, imm increasing from 0 to 8, alusrc=1, aluctrl=0, regwrite=1. This makes aluout and a0 increase together, while eq stays at zero. Next is a count-down phase: we keep a0 fixed at its last value (8), switch to subtraction, and feed decreasing immediates. This causes aluout to decrease until it hits zero, at which moment eq becomes 1 and the LED bar lights up. a0 remains fixed because regwrite is disabled in this phase. Finally, we reset a0 back to zero by doing an ADDI with imm=0. This completes the cycle and repeats.

This Vbuddy demo visually demonstrates that immediate and register operands are selected correctly, arithmetic behaves as expected, the register file stores and preserves values, and the eq flag activates in the correct moment. Combined, the GTest verification provides deterministic logical assurance, while the Vbuddy demo provides intuitive observable behaviour. Together, they confirm that regalu is functioning correctly and is ready for integration into the complete CPU.
